SWS Membership Platform Plan

2026-10-30 · Loren Parfitt

Goal

Replace WellnessLiving with a membership platform the Squamish Windsports Society owns, built as its own project on a Python backend and a React frontend, so that selling passes, gating one pass behind another, and collecting waivers no longer depend on a vendor's admin screens or on editing code each season.

The platform must:

  • Sell a changing catalog of passes and memberships, with early-bird and regular prices, through the society's existing Nuvei merchant account.

  • Gate any product behind prior purchases or other conditions, decided case by case per product, without a code change for each new rule instance.

  • Capture a drawn waiver signature per member, keep an audit record, and let an admin force everyone to re-sign.

  • Check members in at the Spit by scanning the barcodes already printed on current cards.

  • Give staff a kiosk and point of sale, admins a catalog editor and reports, and a partner a limited member lookup.

  • Run on DigitalOcean and be fully testable on a developer's machine.

Architecture

The React app talks only to the FastAPI backend, except for the card form, which Nuvei hosts inside the page so card data never reaches the society's servers. The backend is the only writer to Postgres and object storage. Stack: Python 3.12 with FastAPI, SQLAlchemy and Alembic on Postgres 16; React with Vite and TypeScript; a Nix flake as the single toolchain provider; doit as the single task runner; Docker images on DigitalOcean with Managed Postgres and Spaces.

Data model

The model borrows the Product, Price, Customer, Order and Entitlement split that Stripe settled on, and the versioned-template-plus-signature-record shape of waiver services such as Smartwaiver. Eligibility is never stored: it is computed from entitlements and rules at request time, so it cannot drift.

Gating rule engine

A product is purchasable by a member when every EligibilityRule attached to it passes. Each rule names a rule kind from a closed list in code and carries its parameters as data, so adding a gated product is an admin form while adding a new kind of condition is a small, reviewed code change.

Launch rule kinds:

Rule kindParametersPasses when
requires_active_entitlemententitlement kind, optional season yearThe member holds an active Entitlement of that kind today
requires_current_waivernoneThe member has a WaiverSignature newer than the latest WaiverReset, on the current template
age_at_least / age_at_mostyears, reference date rule (purchase date or season start)Date of birth satisfies the bound

one_per_member_per_seasonseason yearThe member holds no Entitlement from this Product for that season

The evaluation is one pure function: given a Member's active Entitlements, their signatures, their date of birth, the Product's rules and today's date, return pass or the list of failed rule messages. The same function drives the catalog page, which shows why a product is locked, and the checkout, which refuses an order that fails. Staff point of sale runs the same check and can record an admin override with a reason.

Waivers

A waiver is signed by drawing on a canvas, and nothing about a signature is ever edited afterwards.

  1. An admin publishes a WaiverTemplate: title, full document text, and the PDF the member sees. Publishing creates a new immutable version.

  2. A member signing sees the current PDF, types their legal name, and draws a signature on a canvas. For a member under 19 the form also takes the guardian's name and a guardian signature.

  3. The server stores the signature image in object storage, and records member, template version, time, IP address, and a hash of the document text, so the exact wording agreed to can be proven later.

  4. A signature is current when it was made after the latest WaiverReset and against the current template version. Publishing a new template is itself a reset; the admin can also press a reset button, which appends a WaiverReset with a reason and forces every member to re-sign at their next purchase or check-in.

  5. Products that need a waiver carry the requires_current_waiver rule, so checkout blocks until the member signs. The staff kiosk shows a waiver-needed flag on scan.

The member can download a PDF of their signed waiver, rendered from the stored template text plus the signature image.

Payments with Nuvei

Nuvei's Simply Connect flow is used: the server opens the order, Nuvei's checkout script renders the card form inside the React page, and Nuvei's Direct Merchant Notification webhook is the only event that marks an order paid.

  1. The member picks products. The backend evaluates every rule, creates an Order in pending-payment status with its OrderLines, and calls Nuvei's openOrder with the amount in CAD and the Order ID as the merchant reference.

  2. The React page loads Nuvei's checkout script with the returned session token and shows the embedded form. No card data touches the society's servers.

  3. Nuvei posts the notification to the webhook endpoint. The backend verifies the checksum, finds the Order by merchant reference, records a Payment keyed on the Nuvei transaction ID, marks the Order paid, issues the Entitlements from each Product's grants, and emails a receipt through Mailgun. A repeated notification finds the existing Payment and does nothing.

  4. The browser's own success callback only polls the order status; it never changes it.

Staff sales at the Spit go through the same Order path with payment method cash or free and no Nuvei step. Refunds are recorded against the Payment and revoke the Entitlements the order issued.

The Nuvei client sits behind one small payment-processor interface in its own module, so a later processor change touches one file. Before Phase 2, confirm with Nuvei that the merchant account has Simply Connect and notifications enabled; an account provisioned only for the hosted Cashier page means a redirect instead of an embedded form, which the same design supports.

Barcodes and check-in

Existing cards keep working on day one because the member number is WellnessLiving's client number, printed today as a plain Code128 barcode of digits.

  • The import copies each WellnessLiving client's number onto the new Member as member number, along with name, email, date of birth, photo and purchase history.

  • Lookup normalises a scan exactly as the current status check does: strip everything but digits, then strip leading zeros, then match.

  • New members draw numbers from a database sequence that starts above the highest imported number, so no new number collides with a printed card.

  • A scan at the kiosk returns the member's photo, active entitlements, waiver status and today's prior check-ins. Confirming a check-in records a CheckIn and, for a visit-count entitlement, decrements visits remaining.

  • New cards are rendered server-side to the same credit-card PDF layout as today, with the same barcode and the shuttle QR code on the back.

  • The partner lookup replaces the inflow login: a token-authenticated endpoint that answers only member or not a member, rate limited per day, with every call logged.

Phases

WellnessLiving stays live through phases 1 to 3 and is switched off only when the kiosk checks in imported members from their existing cards. Each phase ends with its gate check passing on the real local stack, not a mock.

  1. Foundation. Repo, Nix shell, Postgres, migrations, authentication by email link, roles. Import WellnessLiving clients with their numbers and purchase history. Gate: imported members sign in and their numbers resolve.

  2. Catalog and checkout. Products, prices, entitlement grants, rule engine, Nuvei Simply Connect and webhook, receipts. Gate: one trial product bought in Nuvei's sandbox and then live, with entitlements issued by the webhook.

  3. Waivers. Templates, drawn signing with guardian fields, reset, waiver PDF download. Gate: a product with the waiver rule refuses checkout until signed, and a reset makes a signed member sign again.

  4. Kiosk and cards. Scan and lookup, check-in with visit decrement, card PDF, partner lookup, shuttle page re-pointed. Gate: a current WellnessLiving card scans and checks in; WellnessLiving is switched off.

  5. Admin and reports. Catalog and rule editor, waiver template publishing, batch card printing, titles, sales and attendance reports, season rollover. Gate: next season's catalog created without a code change.

Local development and testing

Everything runs on a developer's machine; nothing in the build needs DigitalOcean.

  • The repo is ~/git/sws-membership. A Nix flake is the one provider of Python, uv, Node and the Postgres client, and uv run doit list shows every action; developers and CI run the same tasks.

  • Postgres runs in Docker through the repo's compose file. Migrations are Alembic and are applied with the migrate task.

  • The API runs with reload on port 8000; the React app runs on Vite's dev server and proxies API calls to it.

  • Tests are pytest against a real Postgres database, not mocks, so entitlement and rule logic is exercised on the schema that ships.

  • Nuvei provides a sandbox merchant environment with test cards. The webhook handler is tested by posting a recorded notification payload with a valid checksum to the endpoint; no public URL is needed for the suite. For an end-to-end sandbox run from a browser, a temporary tunnel exposes the local webhook once.

  • Signature images and card PDFs write to a local directory in development and to DigitalOcean Spaces in production, behind one storage interface.

  • The WellnessLiving import is a repeatable task that reads an export, so it can be rehearsed locally against a copy of the data as many times as needed before cut-over.
